# 职能沟通翻译助手 🚀

> 基于大模型的产品与开发双向沟通翻译工具

一个基于 FastAPI + 通义千问的智能翻译助手，帮助产品经理和开发工程师更好地相互理解，提升跨职能沟通效率。

## ✨ 核心特性

- 🔄 **双向翻译**: 产品需求 ↔ 技术方案
- 🧠 **多角色分析**: 技术架构师 + 开发工程师 + 技术经理三重视角
- 💭 **思维链推理**: 展示完整的分析过程，透明可信
- 📡 **流式输出**: SSE 实时推送，逐字展示翻译结果
- 🎨 **友好界面**: 纯前端实现，无需框架，开箱即用
- 📝 **结构化输出**: 技术方案、业务价值、工作量评估等多维度分析

## 📦 技术栈

**后端**:
- FastAPI (异步Web框架)
- 通义千问 API (大语言模型)
- Pydantic (数据验证)
- Uvicorn (ASGI服务器)

**前端**:
- 原生 HTML + CSS + JavaScript
- EventSource (SSE流式接收)
- 无框架依赖

**Prompt 工程技术**:
- Chain of Thought (CoT) - 思维链推理
- Multi-Persona - 多角色分析
- Few-shot Learning - 示例学习
- Contrastive Prompting - 对比示例

## 🚀 快速开始

### 1️⃣ 环境准备

**系统要求**:
- Python 3.9+
- 通义千问 API Key ([获取地址](https://dashscope.console.aliyun.com/))

### 2️⃣ 安装依赖

```bash
# 进入后端目录
cd backend

# 创建虚拟环境
python3 -m venv venv

# 激活虚拟环境
source venv/bin/activate  # macOS/Linux
# venv\Scripts\activate   # Windows

# 安装依赖
pip install -r requirements.txt
```

### 3️⃣ 配置 API Key

```bash
# 复制环境变量模板
cp .env.example .env

# 编辑 .env 文件，填写你的通义千问 API Key
# QWEN_API_KEY=sk-your-api-key-here
```

### 4️⃣ 运行项目

**启动后端**:
```bash
cd backend
source venv/bin/activate
uvicorn app.main:app --reload --host 0.0.0.0 --port 8100
```

启动成功后，访问 http://localhost:8100/docs 查看 API 文档。

**启动前端**:
```bash
cd frontend
python3 -m http.server 8081
```

访问 http://localhost:8081 即可使用。

## 💡 功能说明

### 这个工具做什么？

职能沟通翻译助手是一个 **AI 驱动的双向翻译工具**，专门解决产品经理和开发工程师之间的沟通障碍。

**核心价值**：
- 产品经理说"我们需要一个推荐功能" → AI翻译成：推荐算法选型、数据来源、技术架构、工作量评估
- 开发工程师说"我们优化了数据库，QPS提升30%" → AI翻译成：用户体验提升、业务增长空间、成本收益分析

### 核心功能

1. **产品需求 → 技术方案**
   - 输入：产品需求描述（如："需要一个智能推荐功能"）
   - 输出：
     - 🏗️ 技术架构设计（3个方案对比）
     - 📊 数据来源和处理流程（技术流程图）
     - ⚡ 性能和实时性要求（量化指标）
     - 👷 开发工作量评估（精确到0.5人日）
     - ⚠️ 技术风险和坑点
     - 💡 反向提问（主动补充缺失信息）

2. **技术方案 → 业务价值**
   - 输入：技术改进描述（如："数据库QPS提升30%"）
   - 输出：
     - 😊 用户体验提升（具体场景举例）
     - 📈 业务增长空间（支持的用户规模）
     - 💰 成本与收益（ROI分析）
     - 📊 可量化的业务指标（百分比对比）
     - 🎯 商业价值总结（竞争力、战略意义）

3. **场景智能识别**
   - 自动识别输入内容是"产品需求"还是"技术方案"
   - 推荐合适的翻译方向


## 🎨 提示词设计说明

### 核心挑战

如何让AI真正理解产品经理和开发工程师的思维差异？

**产品经理关心**：用户价值、商业目标、体验改善
**开发工程师关心**：技术实现、工作量、性能指标、风险

### 设计思路

#### 1. Multi-Persona（多角色分析）⭐⭐⭐⭐⭐

**为什么用多角色？**
- 单一视角容易片面，多角色能全面分析
- 不同角色有不同关注点，组合起来才完整

**产品→开发的3个角色**：
```
【技术架构师】(10年+经验)
- 关注点：系统架构、技术选型、长期演进
- 思维方式：从全局视角看技术方案，预判未来趋势

【一线开发工程师】(5年+经验)
- 关注点：开发难度、工作量评估、技术细节、坑点
- 思维方式：从执行层面看可行性，关注"能不能做"

【技术经理】(8年+经验)
- 关注点：成本预算、ROI分析、团队能力、项目风险
- 思维方式：从资源和商业角度看技术决策
```

**开发→产品的3个角色**：
```
【产品经理】(8年+经验)
- 关注点：用户体验、产品竞争力、用户满意度
- 思维方式：从用户角度看技术改进

【商业分析师】(10年+经验)
- 关注点：ROI、成本优化、收入增长、市场竞争力
- 思维方式：从财务角度看技术投入

【运营增长经理】(7年+经验)
- 关注点：业务规模、增长空间、运营效率、数据指标
- 思维方式：从增长角度看技术能力
```

#### 2. Chain of Thought（思维链推理）⭐⭐⭐⭐⭐

**为什么用CoT？**
- 让AI先思考再回答，提升分析质量
- 展示推理过程，增强可信度
- 帮助AI识别缺失信息

**CoT的4步分析框架**：

*产品→开发*：
```xml
<thinking>
1. 需求理解 - 核心目标是什么？业务价值是什么？
2. 信息盘点 - 已知/缺失/需要假设的点
3. 方案推理 - 有哪些技术方案？适用什么场景？
4. 风险识别 - 主要技术风险？典型坑点？
</thinking>
```

*开发→产品*：
```xml
<thinking>
1. 技术方案理解 - 开发做了什么改进？核心变化？
2. 信息盘点 - 已知指标/缺失业务背景/需要推断的点
3. 业务影响推理 - 如何影响用户体验、业务增长、成本？
4. 价值量化 - 能用哪些数据量化？如何推算ROI？
</thinking>
```

#### 3. Few-shot Learning（示例学习）⭐⭐⭐⭐⭐

**为什么用Few-shot？**
- 示例是最好的老师，稳定输出格式
- 展示"好的翻译"应该是什么样的

**示例设计原则**：
- 完整性：包含所有角色视角、思维链、反向提问
- 典型性：选择常见场景（热门话题榜单、数据库优化）
- 具体性：给出具体数字（3.5人日、ROI 37.5倍）

**提示词中的示例**：
- 产品→开发：热门话题榜单（定时任务+Redis方案）
- 开发→产品：数据库优化（QPS提升，ROI分析）

#### 4. Contrastive Prompting（对比示例）⭐⭐⭐⭐

**为什么用对比？**
- 明确告诉AI"什么是好的，什么是坏的"
- 防止AI输出模糊、泛泛而谈的内容

**对比维度**：

✅ **优秀输出**：
- 至少对比3个技术方案
- 给出具体技术栈名称（Redis 6.0+，而非"缓存"）
- 量化指标（QPS>1000，而非"性能要好"）
- 详细工作量拆分（精确到0.5人日）

❌ **需要避免的输出**：
- 只给一个方案，没有对比
- 使用模糊表达（"需要一个数据库"）
- 泛泛而谈（"性能要好"）
- 忽略工作量评估

#### 5. 反向提问机制（Proactive Questioning）⭐⭐⭐⭐

**为什么主动提问？**
- 产品需求往往不完整，缺少关键信息
- 主动提问能引导产品提供更多上下文

**提问设计**：
```
💡 开发工程师想问你这些问题：
Q1: [具体问题] → 这决定了[技术选型/架构设计]
Q2: [具体问题] → 这影响到[成本/工作量]
Q3: [具体问题] → 这关系到[风险控制]
```

---

### 关键设计点总结

| 设计点 | 作用 | 体现位置 |
|--------|------|----------|
| **Multi-Persona** | 全面分析，不同视角 | 3个角色分别输出 |
| **CoT思维链** | 透明推理，识别缺失 | `<thinking>` 部分 |
| **Few-shot示例** | 稳定格式，质量保证 | 完整示例（热门榜单/数据库优化） |
| **Contrastive对比** | 明确标准，防止低质量 | ✅优秀 vs ❌避免 |
| **反向提问** | 补充缺失，引导沟通 | 💡 4个问题 |
| **技术流程图** | 直观展示，易于理解 | ASCII字符流程图（不写代码） |
| **量化表达** | 具体数据，可验证 | QPS、人日、ROI、百分比 |

## 🔧 常见问题

### Q1: API Key配置问题
**问题**: `ValueError: QWEN_API_KEY is not configured`

**解决**:
1. 确保已创建 `.env` 文件: `cp backend/.env.example backend/.env`
2. 编辑 `.env` 文件，填写你的API Key: `QWEN_API_KEY=sk-xxx`
3. 重启后端服务

### Q2: 流式输出不流畅
**问题**: 翻译结果一次性全部返回，而非逐字展示

**解决**:
- 检查 `backend/app/services/ai_client.py:67` 是否有 `await asyncio.sleep(0)`
- 测试网络连接到通义千问API的延迟

### Q3: 前端无法连接后端
**问题**: 前端显示 "网络连接失败"

**解决**:
1. 确认后端已启动: `http://localhost:8100/docs` 可访问
2. 检查前端API地址配置 (默认 `/api`)
3. 检查CORS配置 (`backend/app/main.py`)
